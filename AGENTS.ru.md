# Инструкции для участников проекта DockFolders

## Продукт и платформа

- DockFolders — нативное приложение macOS для macOS 27.0+ и Apple Silicon (`arm64`).
- Используйте Swift 6, SwiftUI для интерфейса и публичные API AppKit, Carbon или ServiceManagement на границах интеграции с macOS.
- Перед существенными изменениями платформенной части проверяйте доступность и совместимость API в выбранных Xcode и macOS 27 SDK. Не делайте вывод о доступности API только по его названию или примеру из интернета.
- Предпочитайте публичные API Apple и системные фреймворки. Не используйте закрытые API Dock и не изменяйте системный Dock.
- Текущая реализация охватывает функции версии 1.0 и ярлыки отдельных папок. Проверяйте `docs/wiki/Roadmap.md` и `docs/wiki/Implementation-Plan.md` на подтверждения и оставшиеся проверки перед выпуском. Разделяйте реализованное поведение и непроверенные сценарии конкретной системы или выпуска.
- Решение о закреплении приложений в Dock принимает macOS. Не записывайте настройки Dock и не утверждайте, что приложение может закрепить ярлык скрытно. Предоставляйте понятный ручной шаг закрепления и описывайте его в документации.
- Используйте только публичные API Apple. `NSDockTile` настраивает плитку запущенного приложения, но не создаёт произвольные элементы Dock и не закрепляет приложения.

## Проектирование и реализация

- Разделяйте интерфейс, модели и взаимодействие с ОС. Добавляйте протокол на границе ОС или хранилища, если это упрощает тестирование; избегайте универсальных фреймворков и лишних слоёв.
- Атомарно сохраняйте пользовательские папки и сохраняйте прежние данные при ошибках декодирования или записи.
- Показывайте ошибки пользователю; не удаляйте молча папки или записи приложений.
- Используйте структурированную конкурентность и изолируйте состояние UI на `MainActor`.
- Поддерживайте подписи доступности и навигацию с клавиатуры для всех элементов управления.
- Не добавляйте сторонние зависимости без конкретной необходимости.

## Работа и проверка

- Следуйте инструкциям репозитория и пользователя перед изменением файлов. Пользователь просил выполнять все работы непосредственно в `main`; продолжайте работать в этой ветке, пока пользователь не изменит инструкцию.
- Делайте небольшие целостные коммиты. Отправляйте завершённые этапы в `origin/main` и сообщайте коммит и результат отправки. Сохраняйте историю существующих коммитов; не объединяйте коммиты в squash и не переписывайте общую историю.
- Обновляйте `docs/wiki/` и `CHANGELOG.md`, когда этап меняет архитектуру, поведение или статус проекта.
- Вся документация, включая README, инструкции участникам, историю изменений, аудит окружения и Wiki, должна быть доступна на русском и английском. Обновляйте обе языковые версии одновременно.
- Все обязательные страницы Wiki из `docs/wiki/Home.md` должны существовать и соответствовать коду. Отмечайте задачи дорожной карты как `Planned`, `In progress` или `Complete` с подтверждениями; не объявляйте этап завершённым до прохождения критериев приёмки.
- Приложения-ярлыки отдельных папок используют проверенные ссылки `dockfolders://folder/<UUID>` и создаются в `/Applications/DockFolders`. Существующие ярлыки в `~/Applications/DockFolders` переносятся при запуске приложения. Пользователь должен сам закрепить каждый ярлык в Dock. Не изменяйте настройки Dock и не автоматизируйте закрепление.
- Текущее сочетание клавиш — Control–Option–Space; запуск при входе использует ServiceManagement. Не утверждайте, что регистрация ОС или сценарии конфликтов проверены, пока это не проверено вручную на целевой системе macOS.
- Выполните `xcodebuild -list`, чтобы проверить схемы, затем соберите и протестируйте схему macOS командой `xcodebuild`. Указывайте только фактически выполненные проверки.
- Не устанавливайте и не обновляйте инструменты или зависимости автоматически.
- Перед выпуском повторите аудит совместимости toolchain и API.
